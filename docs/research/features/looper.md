# Looper (`HX_LOOPER`, `tools/features/looper.py`, `src/m4/looper.s`)

Changes to the 1 Switch Looper's footswitch, with two settings in Global Settings > Footswitches: Looper Stop>Ply (Press, Release), when a press on a stopped loop starts it, and Looper DblPress (Release, Stock), how long a second press stops the loop. Status tags as in [conventions.md](../conventions.md). The stock footswitch code it works with: [m4/footswitches.md](../m4/footswitches.md#the-1-switch-loopers-footswitch-verified-offline).

- **Decisions** (2026-11-18): Looper Stop>Ply in Footswitches (the unit shows Looper over Stop>Ply), Press (0: stock) or Release (the default: the contributor's call, as the stock clear of a stopped loop plays it first; the cost is a restart from a stop late by the press's length); virtual ID `0xe7`, bits 0..1 of container 115 (`tools/setting_ids.py`), so later looper settings can take the rest of 115. Then Looper DblPress beside it (the unit shows Looper over DblPress), Release (the default, 0: the fix on) or Stock; virtual ID `0xe8`, bits 2..3 of container 115. With long press built they take the last slot of page 5 and the first of page 6, without it page 2. Built into every web build (`WEB` True). The module is where later looper changes go.
- **The hook** [verified offline]: `tools/features/looper.py` owns the state machine's start `0x28d92490` (`own_entry`: its `push {r3-r5,lr}; mov r5,r1` runs from the cave, then a `b.w` to `0x28d92494`); a veneer enters `looper_event` with the stock function in r2, and `looper_event` returns through it as a tail call, with the caller's lr and stack. A chain can't do it, as the handler changes the event the stock function gets. Its only callers are the footswitch handler's press `0x28dd1444`, hold `0x28dd1c6c` and release `0x28dd1d28` (a scan of the code segment for a `bl`, `b.w`, `b<cond>.w` or `blx` to it and for its address as a word), so owning the start reaches the 1 Switch Looper's footswitch and nothing else: the Shuffling Looper (`0x28d923b8`), MIDI CC 60..66 (`0x28de8570`) and the Command Center's Looper commands (`0x28de5a24`) call the verbs themselves. No other feature writes those bytes.

## Stop>Ply

- **Why** [verified offline]: the stock press on a stopped loop plays it at once (`0x28d92502`), and a hold while playing clears the loop only when that press started it (`[looper + 0x66]`, `0x28d9257e`). So a hold to clear a stopped loop plays it for the second it is held, then clears it. The stock double press and hold, which clears a playing loop without playing it again (below), plays a stopped one from its first press to its second.
- **Release, as built** [verified offline]:
  - **The press** of a stopped looper with a loop and the double-press window closed (`[looper + 0x56]` 0, `[+0x60]` set, `[+0x74]` 0), with Stop>Ply on Release (`hxtra_setting_get`, read only for such a press): the window opens (20) and `[+0x66]`, `[+0x67]` go to 1, as the stock press leaves them after its play, but there is no play; a flag holds it for the release. The stock function then gets event 0, which no case takes, so only its common tail runs (the DSP listener's start, `0x28d924a6`).
  - **Its release**, if the looper is still stopped with a loop: Play (`0x28de7c34`), as the stock press calls it, then the stock release, which sees `[+0x67]` set and arms no deferred overdub (`0x28d92562`), and clears `[+0x68]` as it would. A second press while the window is still open stops, as stock; with DblPress on Release the release also sets the window to 21 ticks (below).
  - **Its hold**, if still stopped with a loop: `[+0x68]` goes to 1, so the stock hold takes its stopped path (`0x28d92516..0x28d9252a`): Stop, then `[+0x60]`, `[+0x68]`, `[+0x64]` to 0, the code of the stock double press and hold. Nothing plays. The handler clears its latch before the hold call (`0x28dd1c5a`), so the release that follows never reaches the state machine. UNDO/REDO shows after a hold only while `[+0x6b]` counts down, which the Undo verb starts for about 100 ticks on a 1 Switch Looper (`0x28de7ee8`), from a hold while playing, MIDI CC 63 or a Command Center Undo; so after this clear it shows only when such an Undo came within the last second, as after the stock one. If something else started the loop while the footswitch was down (MIDI, a Command Center command), the flags from the press let the stock hold clear it as stock would; a release then doesn't play. If the looper's code zeroed `[+0x56]` and `[+0x60]` meanwhile (the message handler `0x28de73c4` at `0x28de750a` and `0x28de7524`, as on a preset change), the hold goes to the stock hold unchanged, which does nothing, as stock.
  - Any event of the state machine ends a held-back play. The handler sends a release or hold only for the footswitch whose press it latched (`[obj + 0x80]`, `[obj + 0x81]`), so one flag serves. A release or hold that the handler drops (the footswitch's block no longer a 1 Switch Looper by then, `0x28dd1c5e`, `0x28dd1d1a`) leaves the flag set until the next event of the state machine. A press clears it. A release or hold reaches the state machine first only after a press it never saw (a Shuffling Looper's press, then a preset change back while it is held), and that release would then play a stopped loop.
  - A Stop or Play that MIDI CC 61 or a Command Center command sends while the footswitch is down doesn't change what its release or hold then does: the release still plays a stopped loop, and the hold still clears it. With Press, the press has played already, so such a Stop leaves the loop stopped, and the hold, finding it stopped with `[+0x68]` 0, leaves the loop. The Stop verb on a stopped looper writes nothing the state machine could test (`0x28de7d2a`: the state stays 0; with the looper's MIDI out on, only `[+0x6e]` and `[+0x70]`), so the two cases can't be told apart cheaply (by disassembly, and in unicorn with stand-ins for the verbs).
  - The release-time Play runs outside the widget lock that the stock press's Play runs in (`0x28dd10c0` takes it at `0x28dd10e8` and drops it at `0x28dd1110`, around the press call `0x28dd1444`), from the handler's release path (`0x28dd1d28`) in the same UI task. The stock hold's Stop and Undo (`0x28dd1c6c`) run outside that lock too, as does MIDI's Play (`0x28de85f4`, `0x28de84ee`), and Play touches no widget: it posts to the looper (`0x28de72b8`) and sends MIDI out (`0x28d9bcbc`).
  - Every other press, release and hold, and every event with Stop>Ply on Press, go to the stock function unchanged but for DblPress's window: recording starts and the loop closes on the press, overdub on and off, the double-press stop, double press and hold to clear, hold to undo while playing.
- **Long press**: since PR 166, Foot Switch Long Press gives no Hold action to a footswitch whose blocks include a looper (1 Switch Looper or Shuffling Looper, found with the stock looper predicates), so the looper gets its stock press, release and hold there [verified on unit, by the maintainer in upstream issue 165 and PR 166, with builds without this feature]. So nothing in this feature depends on the footswitch's Hold setting [verified offline, from `action_of` in `src/m4/long_press.s`: with Hold Off it returns no action right after it reads the setting, before it looks for a looper, so that path is as before PR 166; with a Hold set, `hosts_looper` finds the looper and it returns no action]. With FS1 Hold on Tuner on the looper's footswitch, a 1.5 s hold of a stopped loop cleared it without playing and opened no tuner [verified on unit, 2026-11-20, below]. Before PR 166, long press held such a press back and replayed it with its release, which took the looper's hold; reading the code and a unicorn run suggested a double press would then be timed from release to release, but the maintainer's unit run did not show that (a double press stopped the loop with the Hold set and with it Off).
- While a loop plays, the stock double press and hold already clears it without playing it again: the second press stops it (`0x28d92548`, `[+0x68]` 1) and the hold takes the stopped path. Stop>Ply's Release is for a loop that is already stopped.

## DblPress: the double-press gap [verified offline]

- **The stock gap** [verified offline, by disassembly; in unicorn with the real tick]: the press opens the double-press window, `[+0x74]` = 20 (`0x28d924e4..0x28d924e6`), counted from the press. The release of a press that did nothing on a playing loop arms the overdub, `[+0x6c]` = 21 (`0x28d92562..0x28d92564`), counted from the release, and never touches `[+0x74]`: the only writes of `[+0x74]` in the looper's code are the tick (`0x28d92276`), the constructor (`0x28d92352`), the press (`0x28d924e6`) and the double press (`0x28d9254e`), by a scan of `0x28d92000..0x28d93000` and `0x28de7000..0x28de9000`. Each tick (100 Hz, [m4/footswitches.md](../m4/footswitches.md#the-1-switch-loopers-footswitch-verified-offline)) counts the window down first (`0x28d92270..0x28d92276`), then the overdub (`0x28d92278..0x28d92286`), and posts the overdub in the same call when it reaches 0 (`0x28d922bc..0x28d922d0`). So with the first press held d ticks, the window closes 20 ticks after the press and the overdub posts d + 21 after it: a second press in the d + 1 ticks between (at most 21, as it comes after the release) finds the window shut and the looper playing, does nothing (`0x28d924f2` only zeroes `[+0x66]`, `[+0x67]`), and its release, `[+0x67]` 0, arms the overdub anew (21 ticks from that release). The loop overdubs instead of stopping. The same holds after a press that acted (closed the loop, ended an overdub, started playback, or Stop>Ply's play on the release): no overdub is armed, but a second press once the window has shut is a plain press, and its release arms one.
- **The 5 failed stops in 10** the contributor reported come from playing with the installed `next` 2065d7c build (the v1.1.0 features, long press among them), before `looper-dev` was built, with the looper footswitch's Hold Off, so long press played no part. The gap above fits them [hypothesis]: a double press whose second press comes about 20 ticks after the first sits on the gap's edge.
- **DblPress, as built** [verified offline]: at a release that reaches the state machine with `[+0x68]` 0 (every release but that of the press that stopped) and finds the looper playing (`[+0x56]` 1, read after Stop>Ply's held-back play, if any, as that play changes it), with DblPress on Release (`hxtra_setting_get`, read only then; unset or out of range reads its default, Release), `looper_event` sets `[+0x74]` to 21 and hands the stock its release. The stock release then arms the overdub or not, as stock. It writes nothing else: `[+0x6c]` is left to the stock code, so the overdub starts on the same tick as stock. With Stock it reads the setting and writes nothing. In any other state it reads nothing and writes nothing. The press and the hold go to the stock code as before; after a hold the handler drops the release (`0x28dd1c5a`), so a hold leaves the window shut.
- **Why 21** [verified offline]: it is the overdub's own count, and the tick counts the window down before the overdub in the same call, so the call that posts the overdub closes the window too, and every press before that call finds it open: a double press, which stops and zeroes `[+0x6c]` (`0x28d9254e..0x28d92550`), so nothing posts. The state machine can't run inside that call: the event post `0x28db8830` calls the tick and the footswitch handler alike, holding the listeners' lock `0x281f5d8c` over the whole dispatch ([m4/footswitches.md](../m4/footswitches.md#the-1-switch-loopers-footswitch-verified-offline)). Less than 21 leaves ticks of the gap. More would leave the window open after the post, and that is not safe: the post only queues the looper's work item (`0x28d96800`), which the worker task runs later (`0x28de7c00`: it takes `[+0x4c]` and runs the overdub's toggle `0x28de7b24`), so zeroing `[+0x6c]` no longer cancels it, and the toggle would run before or after the press's Stop as the tasks fall: a moment of overdub then Stop, or the toggle on a stopped looper, which still sets `[+0x64]` (undo available, `0x28de7b38`) and, with the looper's MIDI out on, sends its message (`0x28de7b6a..0x28de7b9e`). With 21, a press that comes after the post but before the worker has run finds the window shut and the looper still playing, as on stock at the same moment (in unicorn, with the toggle queued until after the second press, its release, or both: the result equals stock with every pair of values, and 22 fails it).
- **Other states** [verified offline, in unicorn with the real tick]: only a release that finds the loop playing gets the 21 ticks: that of the press that closed the loop, ended an overdub, started playback (Stop>Ply Press on the press, Release on the release) or did nothing on a playing loop and so arms the overdub. Play sets the state to 1 at once on a stopped loop and while recording (`0x28de7cb6`, `0x28de7c6e..0x28de7c70`), as the overdub's end does while overdubbing (`0x28de7bd6..0x28de7bd8`), so such a release finds the loop playing even when it comes right after its press, as with long press [verified offline, by disassembly]. A second press within the 21 ticks stops, even after a first press held 20 ticks or more, which on stock leaves no window: there the second press does nothing and its release arms the overdub. From 21 ticks on it is stock. The release of the press that started recording (state 2) and a release in play once (5, 6) leave the window as stock, byte for byte: a long press that starts recording, then a quick press, closes the loop and plays, as stock. The release of the press that stopped leaves the window shut, so a third press right after a double-press stop starts the loop again, as stock: the Stop leaves the loop stopped, so the state check alone keeps the window shut there. The `[+0x68]` check is for a Play that MIDI CC 61 or a Command Center command sends while that press is down: its release then finds the loop playing and still opens no window, so a third press right after is a plain press on a playing loop and its release arms the overdub, as stock, not a second double-press Stop (in unicorn, with the Play stand-in called between that press and its release).
  - Only the state machine writes `[+0x68]` (`0x28d92526`, `0x28d92542`, `0x28d92554`, `0x28d92588`). If the handler drops the release of the press that stopped (the footswitch's block no longer a 1 Switch Looper by then, `0x28dd1d1a`, as after a preset change with the footswitch down), `[+0x68]` stays 1 until the next release that reaches the state machine. That release, the first of the next double press, then opens no window, so that one double press has the stock gap [verified offline, by disassembly]. This is the cost of the `[+0x68]` check above: without it, that release would open the window as any other release that finds the loop playing.
  - MIDI CC 60..66 and the Command Center's Looper commands call the verbs, which write neither `[+0x74]` nor `[+0x6c]` (the scan above; Stop `0x28de7cf0` writes `[+0x56]`, and `[+0x6e]` and `[+0x70]` with the looper's MIDI out on). So an external Stop or Play inside the 21 ticks leaves the window open, and the next footswitch press is the double-press Stop, which also cancels the overdub still armed. On stock, that press, from 20 ticks after the first press on, is a plain press (Play on a stopped loop), and the overdub still armed then posts and turns the restart into an overdub [verified offline, by disassembly].
- **The four combinations**, from a stopped loop, the first press held d ticks and the second press k ticks after the first release [verified offline, in unicorn with the real tick]:

  | Stop>Ply | DblPress | the first press plays the loop | the second press stops when |
  |---|---|---|---|
  | Press | Stock | on the press | d + k < 20, as stock |
  | Release | Stock | on the release | d + k < 20, as stock |
  | Press | Release | on the press | k < 21 |
  | Release | Release | on the release | k < 21 |

  A later second press does nothing and its release arms the overdub, 21 ticks later, as stock. A 1 s hold of the first press clears the loop as Stop>Ply says, whatever DblPress. From a playing loop Stop>Ply plays no part: Stock stops for d + k < 20, Release for k < 21, and a second press after the overdub's post ends the overdub.
- **The held-back press of footswitch modes 2 and 3**: the dispatch `0x28dd14a0` that reaches the press call is also called from the footswitch handler's work item `0x28dd18b0` (`0x28dd18d4`, `0x28dd18fa`, `0x28dd190c`), which runs a press of FS1..FS3 that the handler holds back 30 ticks while setting 21 (the footswitch mode) is 2 or 3 (`0x28dd1a14..0x28dd1a34`, `0x28dd1fd2`), in the worker task, outside the listeners' lock. A release comes from the handler at once, and reaches the state machine whenever the latch of an earlier press is still set, so it can come before its own press. DblPress would act there: the window that release opens catches its late press, which then stops, where stock gives a plain press, so every second tap would stop [verified offline, by disassembly]. The path reaches the looper only through the stomp toggle, function 2, and the footswitch mode's setter `0x28dd24dc` gives FS1..FS3 function 13 in mode 2 (`0x28dd2570..0x28dd2590`) and 14 in mode 3 (`0x28dd2524..0x28dd2544`) [verified offline, by disassembly]. Whether another writer of the function bytes (`0x28dd511c` has other callers) can leave 2 on FS1..FS3 in those modes was not checked.
