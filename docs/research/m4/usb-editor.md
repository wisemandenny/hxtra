# HX Edit's editor service on the M4

The commands HX Edit sends on its editor stream (service 6) and how the firmware answers them. The host side, transport and message framing are in `tools/hx_ctl.py`'s docstring. Status tags as in [conventions.md](../conventions.md).

## The command table [verified offline, disassembly]

- At boot, `0x28d96adc` calls `0x28e1661c`, which calls one small stub per command. Each stub calls **`0x28e165f0(command, &{handler, check, 0})`**: it refuses a command above `0x7b` and copies the 12 bytes into a table of 20-byte rows at `0x2844ea2c` (`{u8 command, pad, handler, check, 0}`), row = command.
- 110 of the 124 numbers are registered. **Free in stock 3.80: `0x13`, `0x1d`, `0x1f`, `0x20`, `0x26`, `0x2c`, `0x36`, `0x37`, `0x4f`..`0x52`, `0x64`, `0x65`**. Claim one on its line in `tools/usb_commands.py`, the ledger (`tests/test_hxtra.py` fails on a duplicate or a number stock uses, and checks its free list against the stock file); the [screen mirror](../features/screen-mirror.md) has `0x52`, [USB input](../features/usb-input.md) `0x51`.
- `check` validates the parameters; `0x28e19205` (`movs r0, #0; bx lr`) is the one for commands without parameters. Get edit buffer (`0x16`) is registered by the stub at `0x28e1e430` with handler `0x28e1c55d` and that check.

## The dispatch [verified offline, disassembly]

- `0x28e16354(stream, bytes, count, state)` reads a request's map: key `0x66` the seq, `0x64` the command, `0x65` the offset of the parameter (its value is not read here, so it must come last, as hx_ctl packs it). The request it hands on is `{+0 the bytes, +4 their count, +8 the parameter's offset, +0xc u16 seq}`, and a command may keep what it parses at `+0x10` on.
- For row `{first, then, deferred}` it calls `first(stream, request)`; if that is negative it sends the error reply `0x28e15c54(stream, seq, error)` itself. Otherwise it calls `then(stream, request)` when set (negative: the same error reply), else takes a deferred path through the third word (not followed).
- So a command with parameters parses them in `first` and acts and replies in `then`: move a block (`0x2b`) has `first` `0x28e18565` (reads keys `0x4b`, `0x4c` into `+0x10`, `+0x14`) and `then` `0x28e1c491`, which replies with **`0x28e15b30(stream, seq, status, result, [sp] its bytes)`**, a whole reply: `result` a MessagePack nil (`0xc0`) and 1 here. HXtra's commands do it all in `first` and give `0x28e19205` (returns 0) as `then`. The usb-editor names "handler" and "check" below are `first` and `then`.

## A handler [verified offline, disassembly]

- `handler(stream, request)`: `[request + 0xc]` is the request's seq (u16). The stream is an object whose word 0 is a vtable: `[vtable + 4]` = `write(stream, bytes, n)` (negative on error), `[vtable + 0xc]` = `finish(stream, 0)`, which ends the message; `[stream + 0x500]` is the service number. `stream - 8` is the stream's lock (`0x28e24c00` lock, `0x28e24bb0` unlock), held around a reply's writes.
- A reply is built from four per-service getters, each called with the service (6): `0x28e157c8` the reply writer `{context, write(context, bytes, n)}`, `0x28e157ec` the word counting the bytes it holds, `0x28e15810` those bytes (0x64 of them), `0x28e15834` empties them. `0x28e15878(writer, seq, status)` writes the reply map's head: `0x83`, `0x66`, `0xcd` + seq (big-endian), `0x67`, status, `0x68`. The handler then writes the result's MessagePack (Get edit buffer: a str8/16/32 head, `0xda`/`0xdb`, then the blob).
- Then, holding the lock: `write(stream, {u16 0, u16 service, u32 length}, 8)` with length = the writer's bytes + the result's, `write` the writer's bytes, `write` the result's bytes, `finish(stream, 0)`. Get edit buffer writes its blob straight from the serializer's buffer as the third write. The generic sender `0x28e15b30` puts the service at offset 2 of the header.
- A result's bytes may go out over several `write` calls: the stream is a byte stream to the host (`hx_ctl.py` reads a message by its header's length).

## Notify: the events HX Edit hears [verified offline, disassembly]

- `0x28d99820(event, data)` and `0x28d99888()` (event `0x2102`, with `0x40` bytes of its own stack, byte 0 zero) post through the event queue `0x281caa28`: an event taken with `0x28d93884` (no wait: 0 when none is free), with the fan-out `0x28d996bd` and the event at `+0x30`; with data, a 512-byte block of the event pool `0x28120060` (`0x28d93b74`; 32 blocks, the bitmap at `+0x4000`, its lock at `+0x4004`, a semaphore at `+0x400c`) through `0x28d93b14`, which is `0x28d93954(event, 0x40, wait 1)`; then the post `0x28d93918`. With every block taken, `0x28d93954` waits on the semaphore (`0x28d93a92`) with no timeout; only the dispatcher tasks listed at `0x2811ef58`/`0x2811ef5c` get -9 instead. Both return 0 at once while the count at `0x281caa8c` is above 0 ([snapshots.md](snapshots.md)). The stock code of both and of `0x28d99728` is run in unicorn by `tests/test_more_snapshots.py`.
- The fan-out `0x28d996bc(event, id)` hands the event to each listener on the list `0x281caa7c` (lock `0x281caa84`) whose mask shares a bit with the id. Only three places load the list: the fan-out, its set-up `0x28d99740` and the adder `0x28d997d0(node, listener, mask)`, whose only callers are the notify service's (`0x28e13a3c`, `0x28e13ef6`: node `0x2844e8a0`, listener `0x28e13a69`, mask `0x100`; `0x28e13a50` removes it). So these events reach HX Edit and nothing on the unit: the screen and the rings take other paths.
- The notify listener `0x28e13a68` builds a notify message in a block of its own (`0x28e13914`, no wait; it returns 2 when it gets none, and the dispatcher tries again), and that block is freed only once the message is written to the host (`0x28e13874` → `0x28d993b8`, `0x28e1389a`), as the host moves its notify window. So a host that does not read notify fills the pool, and the next post with data waits. Each message is a map of two: key `0x69`, the code, then key `0x6a`, written by what `0x28e15484(event)` returns (the bytes start `0x82 0x69`, the code, `0x6a`: the code is one byte for the events below, and `0xcc 0xfd` for an event the switch does not know). Codes, one event each: `0x2101` → `0x31`, `0x2102` → `0x17`, `0x24112` → `0x24`, `0x44113` → `0x2a`, `0x44117` → `0x2e` [verified offline: the listener run in unicorn (`tests/m4emu.py`; stubbed: its block allocator `0x28e13914`, memset, copy, the stream writer, `0x28e15484`, the send `0x28e138cc`, the free `0x28d93c08` and `0x28d9685c`, which returns 0) for the first `0x40` ids of each of the 13 pages of `0x100` ids its switch compares against: 52 ids give a code each, no two the same]. `0x2101`, a block turned on or off, is posted by the dispatcher (`0x28d95488` → `0x28d94ec8`, its only `movw` at `0x28d95312`), not by select. On the unit (2026-11-20, [features/more-snapshots.md](../features/more-snapshots.md)) the notify stream read by `tools/hx_ctl.py` around snapshot selects carried `0x17`, `0x2a`, `0x2e` and `0x31`, block states as `0x31` (the `0x6a` value naming the block and its state), and never `0x24` [verified on unit] [hypothesis: `0x24112` comes only when a footswitch entry byte changes, which none did between that preset's snapshots, and dev5's quiet selects drop it]. `0x44113` (select's first post) also sets `0x2844e8b9`, cleared by `0x44117` (`0x28d95352`); while it, or `0x2844e8b8` (`0x506` sets, `0x504` clears), is set, the listener drops `0x14110` and `0x4107`.
- On the unit (2026-11-20, [features/more-snapshots.md](../features/more-snapshots.md)) [verified on unit]: `tools/hx_ctl.py` takes notify messages off USB while it waits for each reply, but reads them, which moves the notify window, only when the script drains them. Under a stream of snapshot selects with edit-buffer reads back to back and notify drained every 0.25 s, the build without D stalled USB and came back by itself; dev4, which selected under D, froze (screen, footswitches and Breathing Line; power-cycled, so whether it would have come back is not known). In a later dev4 run that drained notify after each read, USB stopped after presets were changed on the unit, and unplugging USB for 10 s brought it back. dev5, whose selects post nothing under D, stalled USB within seconds in two control runs with no edit-buffer reads, whose script slept 0.2 s and then drained notify for 0.01 s, so for most of the time nothing took notify off USB; the unit answered once the script ended. With reads back to back and notify drained only every 0.25 s it ran without a hang. That the pool was full in these runs is the explanation above [hypothesis: not measured on the unit].
