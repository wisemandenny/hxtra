# Footswitches, key events and MIDI CC bypass [verified offline]

Footswitch functions, key events and holds, the event handler, bypass assignment, controllers, driving a block by MIDI CC, and the 1 Switch Looper's footswitch. Status tags as in [conventions.md](../conventions.md).

## Functions and events

- **Footswitch functions** [verified offline]: `0x28d9607c()` returns `0x28128a70`; footswitch k's function is the byte at `0x28128a74 + 2k`, and 1 is TAP (the footswitch switch at `0x28dd14e0` reaches the tap call `0x28dd1656` for value 1).
- **Key events** [verified offline]: a ring of `{code, value}` reports (`0x28d9aec4..0x28d9af3c`; not the physical footswitches, see the [probes](../features/long-press.md#probes)) feeds `0x28db90ec(code, down)`. That function posts an 8-byte event `{1, code, -, -, type}` through `0x28db8830`, which calls every listener directly (`blx`, `r0` = event, `r1` = the listener's context) under a lock. So a listener can call another listener with an event it builds itself. Types: 1 press; 2 release; 3 release before a hold (posted right after the 2); 5 hold. Each `down` call adds 10000 µs to the key's counter (`0x281f3d5c + 4 * code`). Above `0xf423f` the function posts type 5 once (hold bits `0x281f3d60`), so **a hold is 1 s, for every key**. A release clears the counter. Codes 9..11 are touches on footswitches 1..3, and codes 12..16 are footswitches 1..5 (index = code - 12; 4 and 5 are the external pair).
- **Raw reports per footswitch** [verified offline]: for codes 12..16 the ring loop asks `0x28dd83c4(0x28d96084(), k)` (byte `[obj + 0x28 + 32k]`, set by `0x28dd83e4(obj, k, v)`, which also sends message `0xc10e`; it is set from preset or editor messages, e.g. `0x28dd4698`). Non-zero: value > `0x3f` is down, else up. Zero: each report gives `down` then `up` at once, so the counter never reaches a hold. The stomp release path reads the same byte as "momentary" (`0x28dd1778`: non-zero toggles the block again on release). **[hypothesis]** It is the stock momentary/latching flag. The physical footswitches do not come through this ring (see the [probes](../features/long-press.md#probes)), so the flag does not stop them making holds.
- **Footswitch event handler** [verified offline]: `0x28dd1978(event, obj)`, registered by the literal `0x28dd293c` (its timer callback is `0x28dd18b0`, literal `0x28dd2950`); obj is `0x28d96084()`. It handles types 1, 2 and 5 only. `[obj + 0x78 + k]` is "footswitch k pressed": a press of code 12..16 sets it and calls `0x28dd14a0(obj, k)` (`0x28dd1b94`), unless setting 21 (`0x15`, footswitch mode) is 2 or 3. A release clears it and calls `0x28dd14a0(obj, k)` again (`0x28dd1b7e`, `0x28dd1e82`, `0x28dd1ea0`). `0x28dd14a0` switches on the function byte (1 TAP, 2 stomp: `0x28dd10c0(obj, k)` toggles footswitch k's blocks on press and, if momentary, again on release). A hold of code 12..16 goes to the TBH at `0x28dd1b60` on functions 1..8: 1 (TAP) gives `0x28dd1e70` (guard `0x28d96134(5)`, then the tuner request `0x28d96588`), and 2 (stomp) gives `0x28dd1e18` (acts only when controller `k + 6`'s byte `0x28de6634` is `0xf` or `0x10`). Function 3 and 4 holds do nothing.
- **The function dispatch's cases** [verified offline]: `0x28dd14a0(obj, k)` (obj the event handler's object, `[obj + 0x78 + k]` pressed) reads footswitch k's function byte, sets r0 = `0x28128a70 + 2k` (the byte at +4), r5 = 2k, r3 = byte - 1, and switches with the tbh at `0x28dd14e0` (14 cases); every case exits by `add sp,#16; pop {r4,r5,r6,pc}` or a tail call after the same pop. FS3..FS5 Function's value v is byte v + 1; the value strings (20-byte slots, from Entry 0 file offset `0xc2457` for FS3) are TAP/Tunr, Stomp N, Bank Up, Bank Dn, PresetUp, PresetDn, SnpshtUp, SnpshtDn, FS Mode>, <FS Mode, AllBypas, TogglEXP. On a press: 1 tap core (`b.w` at `0x28dd1656`), 2 toggle k's blocks, 3/4 store the mode in `[obj+0x4d]`, set setting 21 to 2 and call `0x28dd0f44(obj, step)` (step ±1 when the mode was already 2, else 0; **[hypothesis]** opening the bank in Preset mode), 5..8 set `[obj+0x5d]`/`[obj+0x5e]` and act on the release (preset ±1 through `0x28df0248`/`0x28df02fc`, wrapping at 0..125; snapshot ±1 through `0x28de3750`/`0x28de2f90`, wrapping at 0..2), 9/10 step setting 21 through 0..3, 11 `0x28d968b0(1)` when `0x28d96868()` is 0, 12 (`0x28dd1768`, past its press check at `0x28dd17fc`) flips EXP 1/2 (`0x28d96898`, `0x28d968a4`) with a 500-tick popup, then falls into case 2's toggle of k's blocks, which reads `[r5 + 0x78]` with r5 = obj + k. 13 and 14 (14 snapshot k, as Snapshot mode sets it) are not on the menu.
- **The footswitch key task** [verified offline]: footswitch events come from the routine around `0x28db8c20`. It posts whole 8-byte events into a queue with `0x28db88fc` (8 bytes into `0x281f3db0`); `0x28db88a0` drains that queue through the post `0x28db8830`. Each pass adds the time since the last pass (`0x28dadba8`, kept in `0x281f71fc`) to the counter of every key 0..16 whose bit is set in `[0x281f5d98]` and whose hold bit (`0x281f3d60`) is clear (counters `0x281f3d64 + 4k`). Past `0xf423f` it posts type 5 and sets the hold bit. Release (`0x28db8fb6`) posts type 2, then type 3 if no hold fired, and clears the counter and the bits. So **every footswitch makes a hold event after 1 s**, whatever its function.
- **The key queue** [verified offline, disassembly]: `0x281f3db0` is a ring of 8000 bytes (1000 events; set up at `0x28db98e6`, which also puts the first 100 Hz tick, class 3). The put `0x28db88fc(event)` takes the lock `0x281f5d10`, and: a class 2 (knob turn) event adds its clicks to a queued one of the same class and code; a class 6 event replaces a queued one's value; a class 1 event equal to a queued one (its first halfword and its value) is dropped; anything else is appended. Then it unlocks and gives the semaphore `0x281f5d18` that the drain `0x28db88a0` (the UI task) waits on. With fewer than 8 free bytes it stops at a `bkpt`. `0x28db9a58(queue)` is its free bytes, `0x28db9a50(queue)` its used bytes. Eighteen sites put events; [USB input](../features/usb-input.md) puts the host's.

## Bypass assignment, controllers and MIDI CC

- **Bypass assignment and controllers** [verified offline] (details in the long-press branch's research):
  - Bypass assignment is kept per footswitch list, not per block: list head `0x28d96084() + 0x20 + 32k` (`0x28128b4c`). Each footswitch has 8 nodes of 0x38 bytes at `+0xc0 + 0x1c0k`, and the 40 nodes end exactly at the next object (`0x281294cc`).
  - `0x28dd10c0(0x28128a80, k)` walks that list. The press handler's context is `0x28128a80`.
  - Parameter controllers (`0x28d9608c()` = `0x28125d30`): 0 None, 1-2 EXP1-2, 3-7 FS1-5 (FS k is controller k + 3, `0x28dd1228`), 8 MIDI CC, 9 Snapshot.
  - `0x28d96094()` (`0x281252b8`) is the Command Center: Instant 1-6, FS1-5 (6-10), EXP1-2.
  - The Bypass Assign labels (`0x28e3a190`, 8 pointers) and the knob limits (`0x28dbbef0`) stop at FS5 and EXP toe. A block record restore (`0x28dd45ae`) unassigns a footswitch index above 4.
  - So **there is no room for FS6..FS10**.
  - A MIDI CC bypass assignment is driven by `0x28dde408(0x28125d30, 8, cc, value)`, with value a float (the stock MIDI receive at `0x28d9b90e` passes cc value / 127.0; the footswitch path at `0x28dd123a` passes 0.0 or 1.0).
- **MIDI CC bypass, as the virtual footswitches use it** [verified offline]:
  - **Nodes:** controller nodes are `0x28125d30 + 0xac + 0x48i`, i = 0..63. Fields: +0x44 is 0x40 when free; +0x28 is the kind (2 = bypass); +0x10 is the controller (8 = MIDI CC); +0x14 is the CC; +0x2c is the block. The stock MIDI In lookup `0x28ddebcc` reads them under the controllers' lock (`+4`).
  - **Reading a block's state:** `0x28e04514(0x28d92a98(), block, &out)` sets out to 1 when the block is bypassed. It takes the DSP-model lock itself, and leaves `out` unwritten for an unknown block. The stock toggle at `0x28d9489c` gets the state, then sets the opposite with `0x28e045a0`.
  - **Driving a CC:** `0x28dde408(0x28125d30, 8, cc, value)` drives every assignment on that CC. The value is float bits in r3: below 0.5 bypasses, 1.0 turns the block on. That is the stock MIDI receive's path (`0x28d9b91a`, CC value / 127.0), and the footswitch toggle calls it from the event handler (`0x28dd123a`).
  - **Which CCs:** MIDI receive (`0x28d9b89c`) keeps CC 0..3, 32 and 49..81 for global functions. Every other CC, 102..106 included, goes to `0x28dde408`.

## The 1 Switch Looper's footswitch [verified offline]

By disassembly of the stock 3.80.0 code segment. A tick is 10 ms: the looper's tick is a listener of the class-3 event, the 100 Hz tick that [screen-mirror.md](../features/screen-mirror.md)'s input capture logs on the unit. HXtra's Looper Stop>Ply and DblPress: [features/looper.md](../features/looper.md).

- **The looper object**: `0x28d9609c()` returns `0x281298dc`. `[+0x56]` its state (0 stopped, 1 playing, 2 recording, 3 overdubbing, 5 play once, 6 overdubbing in play once), `[+0x60]` a loop is recorded, `[+0x64]` undo is available, `[+0x65]` the DSP listener is on, `[+0x66]` this press started playback, `[+0x67]` this press acted, `[+0x68]` the second press of a double press is held, `[+0x6b]` the UNDO/REDO popup's countdown, `[+0x6c]` the deferred overdub's countdown, `[+0x74]` the double-press window (a word). Only the state machine reads or writes `[+0x66]`..`[+0x68]` (the constructor `0x28d922d8` zeroes the whole object).
- **Its tick** `0x28d92264(-, looper)`, registered as `lv-tck` with class 3 (`0x28d92370..0x28d92382`): the event post `0x28db8830` calls it for each tick, as it calls the footswitch handler for a key event, and holds `0x281f5d8c` (taken at `0x28db883a`, given at `0x28db8880`; the listener registration `0x28db9648` takes it too, so it is the listeners' lock) over the whole dispatch, so the state machine never runs inside a tick. In one call it counts `[+0x74]` down to 0 (`0x28d92270..0x28d92276`), then `[+0x6c]` down, posting the deferred overdub when it reaches 0 (`[+0x4c]` |= 0x20, then `0x28d96800(looper + 0x30)`, `0x28d922bc..0x28d922d0`); `[+0x6b]` the same way with 0x40. The post queues the looper's work item (its function `[+0x38]` = `0x28de7c00`) on the work queue `0x28124208`, whose task takes and clears `[+0x4c]` and, for 0x20, runs `0x28de7b24` (`0x28de7c16..0x28de7c1e`), the overdub's toggle: playing to overdubbing, and on any state it sets `[+0x64]` (`0x28de7b38`).
- **The state machine** `0x28d92490(switch, event)`: it ignores its first argument; 1 is a press, 2 a release, 5 a hold, and every event ends in a common tail (`0x28d924a6`) that starts the DSP listener once (`[+0x65]`); any other event runs only the tail.
  - **Press**: with the window open, Stop (`0x28de7cf0`), the window and `[+0x6c]` to 0 and `[+0x68]` to 1: a double press. Else it opens the window (20 ticks). With no loop, Rec (`0x28de77b8`). Else `[+0x66]` and `[+0x67]` go to 0, then: recording, `[+0x67]` 1 and Play (`0x28de7c34`), which closes the loop; overdubbing, `[+0x67]` 1 and the overdub's end (`0x28de7b24`); stopped, Play and `[+0x66]`, `[+0x67]` to 1 (`0x28d92502..0x28d9250a`); playing or play once, nothing.
  - **Release**: playing with `[+0x67]` 0 (a press that did nothing), `[+0x6c]` to 21 (`0x28d92562`): the overdub posts 21 ticks after the release, unless a second press in the window cancels it. Then `[+0x68]` to 0. The release leaves the window, which closes 20 ticks after the press, so with the press held d ticks there are d + 1 ticks (at most 21: the ticks from the release to the post), from 20 to d + 21 after the press, in which a second press is neither a double press nor after the overdub: it does nothing (playing), and its release, `[+0x67]` 0 again, arms the overdub anew, 21 ticks on. A double press with a slow first press overdubs instead of stopping: [features/looper.md](../features/looper.md#dblpress-the-double-press-gap-verified-offline).
  - **Hold**: stopped with `[+0x68]`, Stop and `[+0x60]`, `[+0x68]`, `[+0x64]` to 0 (`0x28d92516..0x28d9252a`): the double press and hold clears the loop. Playing with `[+0x66]`, the same (`0x28d9257e..0x28d9258c`), so a press and hold on a stopped loop plays it for the second it is held, then clears it. Playing with undo available, Undo (`0x28de7e44`), which sets `[+0x6b]` (`0x28de7ee8`); nothing else sets it.
  - Play on a stopped looper plays only when `[+0x60]` is 1 and sets the state to 1 at once (`0x28de7cb6`); Stop sets it to 0.
- **Its callers** (a scan of the code segment for a `bl`, `b.w`, `b<cond>.w` or `blx` to it and for its address as a word): the footswitch handler alone. The press `0x28dd1444`: the stomp toggle `0x28dd10c0(obj, k)` finds a block of model 504 or 505 (`0x28de778c`) on footswitch k, latches it (`[obj + 0x80]` 1, `[obj + 0x81]` k, `0x28dd1432`) and calls it with (k, 1). The hold `0x28dd1c6c` and the release `0x28dd1d28` run only while the latch is set and the event's code is `[obj + 0x81]` + 12; each clears the latch first (`0x28dd1c5a`, `0x28dd1d14`), checks that the footswitch's block is still a 1 Switch Looper, then calls with (code, 5) or (code, 2). So the release after a hold never reaches it. The Shuffling Looper (models 570, 571, 616 and 617, `0x28de779c`) goes to `0x28d923b8` instead. After the hold call the handler shows UNDO/REDO (`0x28dd2018`) when `[looper + 0x6b]` is set (`0x28dd1c80..0x28dd1c8a`).
