# Model blobs and parameter maps

What a model is made of: its parameters in Entry 3, its blob's node tree and parameter map in Entry 4, and its row in Entry 0; adding a parameter; tempo sync. Status tags as in [conventions.md](../conventions.md).

## Model parameters (Entry 3, Entry 4 parameter map, Entry 0 info row) [verified offline]

- A model's parameter count has to agree in three places: Entry 3's descriptor (`d[7]` parameters, `d[6]` states), the blob's parameter map (one input node and one slot-map entry per parameter), and the Entry 0 UI Model Info Table row (bytes 24..35, three counts).
- Parameter map header: offsets of tables A (nodes), B, C (edges), D (slot map), E and F at words 0, 2, .. 10; sizes at 12..17; counts nA..nF at 18..23. The sizes follow the tables in every map checked: sum of node state words, nA, nD + sum n_out + inputs, nC + nD + inputs, nD, nE.
- Deluxe Comp (blob 68 mono, 349 stereo): seven input nodes, op `0xa` float or `0xb` int (Ratio). Slot map {node, state index, slot, 0}; state index = the input's rank in node order, matching Entry 3's state records `{0, 0x80b98, name, type, index}`. Root init records `{path [1, 0], slot, value, kind 1}` give each slot's default.
- `tools/patch_comp.py` adds GR Position, GR Direction and GR Thickness (int lists, slots 8..10) to both Deluxe Comps. The new input nodes have no edges, so the DSP is unchanged. Entry 3's tail string section grows in place, and the model table and everything after it move down. The blob's map, init records and relocation list are rebuilt after the node tree.

## Map tables B and F, curves and nested maps [verified offline]

Found with `tools/sharc/pmap.py` (2026-11-19), which applies all of this to any model and prints each knob's path to the primitives it sets; checked on all 61 mono distortion and 8 mono EQ models and the four splits, and since 2026-11-25 run over all 830 effect models of every category (`tests/test_pmap.py`).
- **Node record** (table A, 10 words): `{data_off, 0, id, op, n_out, state words, data len, data len, is_input, 0}`. Writers (op 1) point at `{path_off, pid, 1}`; `path_off` is blob-relative, the path is `{len, slot, slot, ..}` (`[1, 6]` = top-level slot 6, `[2, 3, 7]` = slot 7 inside the composite at slot 3, `[0]` = the root itself).
- **Table B** holds curve tables: 6-word rows `{data_off, 0, node id, 0, count, 0}`, the data after the rows. Every op `0x3` node (715 in these 69 models: 11 state words, no data of its own) has a row with **9 values**: the output at knob 0, 1/8, .., 1 of a 0..1 knob. Teemah! Level: −60 dB at 0, 0 dB at 5/8 = 0.625, its default 0.63 [verified offline]. Between the points the output is linear (op `0x3`'s code, below) [verified offline].
- **Table F** has one 8-word row per child of the map's composite in the blob's node tree (`nF` = their number), in tree order, which is not always member order. A row is filled, `{map_off, 0, ..}` with `map_off` the pm offset of that child's own map (same 24-word header, pm-relative offsets), exactly where the child is a composite; all others are zero (Minotaur: three, for slots 2, 3, 4; Teemah!, Scream 808: one, slot 3; Xenomorph Fuzz: one, slot 15). This holds at every level, nested maps included, in all 830 effect models [verified offline 2026-11-25, `tests/test_pmap.py`]. In the 41 cabs a composite comes later in the tree than in member order (1x12 Blue Bell: member 23 before member 20), so pairing maps with composites in member order gives the wrong knobs there. A composite member with no node-tree entry has no row and no map and runs on its init values (Simple Delay's `0x6000d7`, Barberpole's and Frequency Shift's `0x6000c5`). A writer to a composite's path with pid k feeds the nested map's slot k; a slot nothing writes takes the blob's init record for that path and pid. So knobs that reach a sub-composite resolve offline like any other.
- Ops seen on knob paths in these 69 models (occurrences in the knobs' expression trees, a node shared by two writers counted twice): `0x3` (725), `0x36` (79), `0x2b` (63), `0x14` (42), `0x3a` (39), `0x4e` (23), `0x45` (17), `0x38` (16), `0x1b` (14), `0x40` (13), `0x1c` (10), `0x18` (9), `0x1d` (7), `0x58`, `0x44`, `0x27` (5 each), the rest at most 3.

## Map ops [verified offline unless tagged]

Found 2026-11-19. The ops are SHARC registry rows like the primitives (DM `0x200000`, 8-word rows `{id, eval, …, state words}`); the small ids are the map ops. An op's eval function gets R4 = the node's state, R8 = the port that changed, R12 = a pointer to the new value, and passes its result on through `CJUMP 0x178ef2`. Code read by hand from `tools/sharc/visa_dis.py` (VISA short-word addresses around `0x17b4ed`..`0x17bc40` and `0x616a50`..`0x6178b8`).
- **Ports and data words.** A two-input op's init (`0x616a7f`) puts data word 0 on port 0 and word 1 on port 1; an edge into a port replaces its word, so word 0 is a placeholder wherever a knob feeds port 0. The "hot" variants (init `0x616a50`) recompute only when port 0 changes and carry one data word, port 1's. Selects carry one word per choice: `0x36`'s init (`0x61869e`) puts its four on ports 1..4. Every node in the 69 models fits this (e.g. `0x14` data (0, −1.0) with an edge on port 0 = x − 1; `0x2b` data (−120, 0) with an edge on port 2).
- **Curve** `0x3` (eval `0x6178b8`): x clamped to 0..1, t = 8x, i = ⌊t⌋, out = T[i]·(1 − r) + T[i+1]·r with r = t − i and T the node's 9 values in table B.
- **Arithmetic** (port 0 = a, port 1 = b; hot variant in brackets): `0x14` (`0x1b`) a + b, `0x1c` integer a + b (`0x15` presumably its non-hot form, not traced), `0x18` (`0x1d`) a·b, `0x19` (`0x1e`) integer a·b, `0x45` (`0x46`) a / b, `0x47` (`0x48`) b^a, `0x2c` min, `0x2d` max.
- **Tests** (1 or 0): `0x3d`, `0x3e` (`0x3f`, `0x40`) a > b, integer and float; `0x41`, `0x42` (`0x43`, `0x44`) a = b. Logic: `0x4e` NOT, `0x57` AND, `0x58` OR.
- **Selects**: `0x2a`, `0x2b` port 0 ? port 2 : port 1; `0x35`, `0x36` port 0 (clamped to 0..3) picks ports 1..4; `0x37`, `0x38` the same with 8 (clamped to 0..7).
- **Conversions**: `0x23` int → float, `0x24` truncate, `0x25` ≠ 0, `0x26` copy, `0x27` dB → linear (10^(x/20), 0 at −120 dB or below), `0x28` linear → dB (20·log10, −120 for 0).
- **[hypothesis]** `0x3a` (data 0, 8.0; calls expf with −2π and 1000): a one-pole smoother whose settled value is its input. `0x6` (two inputs, a 3 × 3 table, Megaphone only): bilinear over the table. `0x2` (no inputs, data 1, 33, 1): reads a run-time value (Horizon Drive's gate), `0x17` and `0x39` (Jet Fuzz Rate): an LFO; none of these four was traced.
- `tools/sharc/pmap.py --sweep` evaluates every writer with these rules: each knob at min, ¼, ½, ¾, max (switches 0/1, lists every entry), the others at their defaults.
- Writers to the root (`[0]`, pid 0..4) occur in five models. In Parametric and Low and High Cut they come from the cut knobs: Low Cut ≥ 20 Hz gives 1, the 19.9 Hz "Off" end 0; High Cut ≤ 20 kHz gives 1; the others are Bitcrusher, Obsidian 7000, Clawthorn Drive. They are on/off flags, **[hypothesis]** the bypass of composite members (pids 0, 1 the two low-cut sections, 3, 4 the two high-cut ones). For Clawthorn Drive and Bitcrusher the writes are switches (writer kind 0, counted in header word 0).

## The node tree

- **A model blob's node tree overrides member primitives** [verified offline, and on unit by the Kinky-knobs and Kinky-2710 images in the [GR meter log](../features/gr-meter-log.md)]: entries `{slot, type, child_off, child_cnt}` after the root, `type` `0xffffffff` for none; slot k is path [k], member k − 1. The Kinky Comp's core (slot 14; stereo 23 and 33) is **`0x2710`** there, not blob 0's `0x2719`; slot 9 is `0x2711`. The LA Studio Comp overrides slot 13 to `0x239e` only. `0x2710` (registry `0x200180`) shares the process code `0x8d342` with `0x2719` but has its own control function `0x60cf8e`; the Sweep Echo delay (composites `0x6000d4`, `0x600024`) uses it too. The LA Studio Comp and the Red Squeeze share composites (`0x6000ca` mono, `0x60001d` stereo).

## Sub-bindings and table F [verified offline]

Checked on all 863 stock model blobs (2026-11-19, each taken apart and laid out again by a script).
- Blob layout, always in this order: header (12 words: 3, a word kept as is, node tree offset and count, init-record relocations offset and count, parameter map offset and length, sub-bindings offset and count, init records offset and count), path and value area, node tree, parameter map, init records, relocations, sub-bindings. The node tree puts each node's children in one block and lays the blocks out depth first. Taking a blob apart and laying it out again this way gives every stock blob back word for word.
- **Sub-bindings** (header words 8, 9) are pairs `{member path, position path}`, one per node-tree node under the root. The position is where the node sits in the tree: `[i]` is the root's i-th child, `[i, j]` that child's j-th child (Teemah!: `[1, 3]` → `[1]`, the drive's `[2, 3, 6]` → `[1, 1]`). Writers name member paths. 16 564 of 16 566 top-level writers go to a slot that is a root child; the two others are in the Loopers.
- In 836 blobs some path words serve as both a member path and a position path. So renumbering member paths in place moves positions too.
- **Table F** has one 8-word row per root child (`nF` = their number in 863 of 863), in tree order; a nested map's table F likewise one per child of its node (above).
- Relocations cover every init record and every writer's path word, nested maps' included; sub-bindings and init-record values are not relocated.

## Tempo sync in a parameter map [verified offline]

- Stock Simple Delay (blob 50) gets its delay time from the tempo inside its parameter map, with no M4 code of its own. Its Time knob comes as three Entry 3 parameters: the float `Time` (slot 1; meta `sync` 1, `coupledIndex` 10, `toggleSelectIndex` 11), the int note list `SyncSelect1` (slot 10, values 1..19 = 1/1 .. 1/64 Triplet, 6 = 1/4; meta `persistent` note) and the bool `TempoSync1` (slot 11). Entry 0's Table 2 row counts them (4, 6, 6): the last two are hidden, as `displayParamCount` 4 says.
- The map: `TempoSync1` into a node of op `0x2a` (4 state words, data 0, 0) at port 0, `SyncSelect1` at port 2 (port 1 is free on delays); `Time` into a node of op `0x54` (9 state words, data min, max = 0.00035, 8.0) at port 0, the `0x2a` node at port 1; then op `0x2d` (data 0, 0.00035) and a writer to the delay member's pid 1. Edges are `{src, dst, src port, dst port}`. 344 stock `0x2a` nodes all have data (0, 0); `0x54` follows each in the delays with that model's time range.
- **[hypothesis]**, borne out by the Metronome working on the unit: `0x2a` gives the note's length in seconds at the current tempo while `TempoSync1` is on, and `0x54` takes that or the free `Time`, clamped. `0x2d`'s job is not known (its second word is the clamp's minimum in the delays).
